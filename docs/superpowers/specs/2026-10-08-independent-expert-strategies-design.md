# 两种主动悬架专家策略的独立开发架构

日期：2026-10-08。状态：架构方向已获用户确认，本书面设计待审阅；尚未实施。

## 1. 任务与场景定义

在当前 TruckSim–Python 工程内同时维护抬轮过深坑与下压过浅坑两个专家策略。两者使用完全相同的控制对象，共享求解器、信号接口、场景构建与原生动画/视频基础设施，但控制逻辑、调参、辨识结果、验收和运行输出分别维护。

用户已经明确：单轮坑不是整次任务只有一个轮经过。单侧坑位于右侧轮迹，FR、RR 依次通过；宽坑覆盖左右轮迹，FL/FR 先通过，RL/RR 后通过。不能把宽坑解释为右侧前后轮，也不能直接套用深坑单侧宽度限制。

浅坑任务从坑前静止初始化开始，通过主动悬架和四轮转矩控制蠕行驶出；最终控制策略应满足不触底、不侧翻、不持续打滑、不跑偏和不爬坑失败，并评估平顺性。本次范围是架构整理、旧策略迁移、浅坑开发框架及场景/显示通路；不实现或宣称浅坑控制策略已经成功。

浅坑具体深度、纵向长度、横向宽度、蠕行速度和舒适性阈值尚未由用户指定。架构使其显式可配置，不将临时示例参数标记为推荐工况，不阻塞本次架构工作。

## 2. 当前工程事实与迁移约束

- 项目根目录是 `Research/TruckSim仿真`，不是上层研究资料目录。设计调查时 HEAD 为 `aff78ba`，工作区干净。
- 当前唯一车型为 I_I Compact Utility Truck，FL/FR/RL/RR 对应 L1/R1/L2/R2；当前成功循环使用了隔离副本的载荷、回弹止挡、运动学表及低速轮胎修订。
- `scripts/run_static_fr_closed_loop.py` 包含模型准备、FR 控制和验收；`scripts/run_right_side_full_cycle.py` 导入该脚本，并通过赋值 `front_run.CFG` 改变模块全局配置。
- `src/ddevsim/static_wheel_lift/` 已包含大量经过验证的控制实现。保留其物理算法与已验证参数，不在整理时重新调参。
- `configs/recommended_right_side_20261005.json` 是当前推荐清单；旧启动脚本的默认清单与推荐清单不同，兼容入口必须保留原默认语义。
- 原基础模型有八路执行器输入，完整循环副本还有第九路方向盘角。不得将当前八路合同悄悄改为九路；显式声明两种接口能力。
- `cosim.run_stepwise` 使用原生 DLL 并改变进程工作目录。两次原生仿真必须隔离进程，不能用线程同时运行。
- 原生动画通过 `.vs/.vsb/*_all.par` 及场景资源播放，视频准备工具已有 ASCII 暂存和默认隐藏驾驶员机制。

## 3. 目录与依赖边界

目标结构如下。现有低层模块无需为了目录外观全部搬迁；共享职责必须明确，新的共享模块不得依赖任何策略实现。

```text
src/ddevsim/
  strategies/
    wheel_lift/          # 前轮/后轮控制、完整循环、专属运行与验收
    shallow_press/       # 浅坑控制开发接口、专属配置与验收入口
  runtime/               # 策略合同、运行身份、输出隔离、策略选择
  scenarios/             # 规范化场景、物理地形与显示资源构建
  vehicle_profiles/      # 同一车型版本的声明与生成规则
  static_wheel_lift/     # 保留旧策略专属底层算法的兼容位置
  cosim.py, solver_api.py, channels.py, units.py
  native_video.py, visual_mesh.py, replay_video.py
configs/
  wheel_lift/            # 新策略入口的参数清单
  shallow_press/         # 单侧浅坑和宽浅坑开发配置
scenarios/
  wheel_lift/
  shallow_press/
tests/
  architecture/          # 依赖、配置、身份、输出隔离与兼容测试
  shallow_press/         # 浅坑框架与场景测试
runs/<strategy>/<case>/<run_id>/
docs/ARCHITECTURE.md
docs/STRATEGY_DEVELOPMENT.md
```

依赖方向为：命令入口 → 策略选择/运行层 → 指定策略与共享基础设施；策略 → 共享合同/基础设施。两个策略不得互相导入，也不得导入 `scripts/`。共享层不得导入策略专属配置、状态机或增益。

已有 `scripts/` 是兼容命令入口。迁出其可复用控制器与模型准备职责后，它们仍接受原参数、返回原结果字段，保留测试和其他诊断脚本需要的兼容导出。

历史证据、模型文件、清单和报告不批量移动或重写。早期 `expert_controller.py` 明确标记为历史移动过坑实现，不作为两个当前策略的默认入口。

## 4. 车辆版本与场景独立

为当前已验证的调参 I_I 控制对象声明一个不可变的车辆版本。固定质量/载荷位置、悬架几何和止挡、轮胎低速处理、运动学处理、输入能力以及积分步长。既有 CLI 中的诊断变体仍可显式使用，但必须产生不同车辆身份；浅坑开发默认与已验证抬轮配置选择相同车辆版本。

车辆身份与场景身份分别记录。场景变化只允许改变路面、初始位置、仿真终止时刻和显示参数；不得隐式改变车辆参数。参数按生成规则和实际产物记录，不只依赖名称。既有辨识的完整模型哈希校验继续有效；新身份划分不能使旧增益自动获得新的复用资格。

场景合同明确使用：坑深 `depth_m`、沿行驶方向长度 `length_m`、横向宽度 `width_m`、横向中心 `center_y_m`、坑口位置、边缘过渡、附着、坑前起点、初始速度和预计经过轮位。轮位用于核查而非替代实际接触几何。

单侧浅坑覆盖右侧轮迹；宽浅坑覆盖左右轮迹。通过轮迹/轮胎包络和边缘过渡校验实际覆盖，不能仅用场景名称判断。起点必须使车辆静止且全部轮胎位于坑前固地。

物理路面、TruckSim 显示形状与 OBJ 网格来自同一个场景对象。显示微小偏置仅用于渲染，不能进入物理坑深或验收。

## 5. 策略接口与配置

定义带版本的 `StrategyContext`、`Observation`、`ControlCommand`、`StrategyStatus` 和策略协议：

- 初始化或 `reset(context)`：接收冻结车辆/场景身份、明确控制周期、不可变配置和显式辨识/参考资产路径。
- `step(observation)`：接收带仿真时间、观测时间、有效性及单位声明的观测，返回四轮转矩、四角主动悬架力，以及在车辆版本支持时的方向盘角。
- 状态接口：返回阶段、完成标志、异常原因；禁止以字符串阶段名称让共享层推断某一策略的控制行为。
- 结束/汇总接口：输出算法遥测和策略专属验收结果，与求解器完成状态分开。

轮序固定 FL/FR/RL/RR。新公共接口使用明确 SI 单位，转向使用显式命名的方向盘角，转换发生在原生适配边界。旧抬轮适配器保留既有原生单位与数值运算，避免重构改变已验证轨迹。

所有可变控制状态归属于实例；配置通过构造参数传递。删除运行路径中修改模块全局 `CFG` 的行为。共享不可变默认值可以保留，但实例初始化或 CLI 参数不能改变其他实例的默认值。

策略注册通过显式标识选择 `wheel_lift` 或 `shallow_press`。浅坑控制律尚未实现时，场景准备、合同检查和显示资源准备可以运行；请求原生控制仿真必须明确报“策略尚未实现”，不得静默运行抬轮策略、零输入策略或输出 PASS。

## 6. 文件、进程与开发隔离

新运行目录为 `runs/<strategy>/<case>/<run_id>/`，包含 `model/`、原生历史、控制日志、`result.json`、`run_manifest.json` 和 `video/`。旧入口显式指定的 `--output` 保持有效。

用原子独占创建认领运行目录；已存在的目录拒绝覆盖。每次运行冻结实际车辆/场景/配置和来源哈希、策略标识、代码版本/工作区状态、随机种子、通道顺序、控制与积分周期。

生成器只写入该次运行模型副本。车辆源模型、另一策略配置、参考增益及历史证据不得作为输出目标。视频暂存/导出路径包含运行身份，两个策略不得共享固定中间文件名所在目录。

原生求解器每次仿真独立进程。若 TruckSim 许可证不支持并发求解，排队或明确返回许可证错误；算法独立开发不等于保证许可证支持同时仿真。

开发约定写入项目级说明：分别维护策略目录与专属配置；修改公共接口必须保持兼容或显式提升版本，并回归两侧合同。并行编辑相同公共文件仍需协调；运行和依赖隔离可以通过测试保证，不能承诺任意同时修改同一 Git 工作区文件均无冲突。

## 7. 动画、视频与验收

共用原生历史定位、ASCII 暂存、资源准备、驾驶员隐藏、VS Visualizer 启动和视频导出工具。新运行目录需能被现有播放工具识别。保留工程回放与原生视频的区别；既有原生 AVI 最终 GUI 导出步骤不在本次架构重构中改造。

抬轮验收保留现有离地、三支撑、净空、路径、反馈健康和恢复规则及阈值。浅坑验收不复用抬轮成功判据：后续分别定义悬架止挡、车身/底盘触地、稳定性、低速滑移、路径偏差、驶出与舒适性指标。不可观测的量必须标为未评估；悬架行程不能冒充车身底盘净空，求解完成不能冒充任务成功。

共同结果区分运行状态、任务成功、异常恢复和各指标是否已评估。浅坑框架没有完整控制与验收时不输出任务 PASS。

## 8. 验证与交付条件

1. 记录重构前 Python 测试结果与推荐运行命令；重构后运行全部既有测试，补充有实际隔离意义的测试。
2. 同一进程先后创建不同配置的抬轮实例，验证配置/状态无泄漏；检查新策略互不导入、共享层不依赖专属策略。
3. 对迁出控制器的确定观测序列比较重构前后输出与状态；原生验证按固定同工况比较，而非仅比较 PASS 字段。
4. 模型准备前后检查源资产哈希；两种浅坑改变坑深/覆盖时，车辆版本保持一致。分别校验单侧与宽坑物理地图、显示网格和初始化位置。
5. 验证重复运行目录拒绝、两个策略输出隔离、完整清单身份记录和未实现策略明确拒绝运行。
6. 回归旧运行命令参数/默认值、既有结果字段、显示默认隐藏驾驶员与历史原件保持；检验新目录的历史发现与显示暂存。
7. 在本机许可证可用时执行代表性抬轮原生回归和新场景显示验证。许可证/Visualizer不可用时明确记录未验证项，不宣称原生行为已经保持。
8. 更新 README 的当前入口和目录说明，增加架构与新策略开发说明，保留历史复现入口。

交付完成是：两个策略有独立、可执行检查的开发边界；抬轮可通过兼容入口运行；浅坑两类场景可准备并接入共用显示链路；新的浅坑控制律拥有清晰扩展接口。浅坑任务成功属于下一阶段开发的验收目标。

## 9. 实施顺序约束

先冻结旧基线并建立隔离合同，再抽取抬轮脚本职责和显式配置，随后接入新运行组织、浅坑场景与开发接口，最后做回归和文档核查。禁止在结构调整时同时调抬轮参数或宽松化验收。详细文件级改动及验证命令将在书面设计审阅后写入实施计划。
